### Task A.1 — Wire real `loc_added` / `loc_deleted` in both walkers (CRITICAL)

**Validated state:**
- `crates/codelore-lib/src/repo/gix_repo.rs:189` carries a docstring "*For Plan 1 we set `loc_added`/`loc_deleted` to 0 and `hunks` to empty*"; lines 254, 265, 276, 304 all literally `loc_added: 0, loc_deleted: 0`.
- `crates/codelore-lib/src/repo/git_cli_repo.rs` runs `git log --name-status` (line 59) which doesn't emit line counts; lines 401, 412, 428 hardcode `0`.

**Impact:** every churn-driven analysis in v0.1.0 returns zero added/deleted lines: `abs-churn`, `author-churn`, `entity-churn`, `main-dev` (by-added-lines ranking is meaningless when every author ties at 0), `entity-ownership`, the `code-health` churn-rate penalty term, and the Kamei `la`/`ld`/diffusion features.

**Why the parity tests didn't catch this:** suspected — code-maat reading the same `--name-status` output also produces zeros, so a parity assertion (`codelore_csv == cmaat_csv`) passes trivially at `0 == 0`. Validate this hypothesis before fixing.

#### Sub-tasks

- [ ] **A.1.1 — GitCliRepo: switch `git log --name-status` → `git log --numstat`.** `--numstat` emits `<added>\t<deleted>\t<path>` per change line. Binary files yield `-\t-\t<path>`; coerce both to `0` and capture a `binary: bool` flag if it ever proves useful. Update the line parser at `parse_name_status_line` (`git_cli_repo.rs:384`) — rename to `parse_numstat_line` and rewire from the `name_status` callers. The renames are detected separately via a `--summary`/`--diff-filter` combination OR by keeping `--name-status` alongside numstat (`git log --name-status --numstat` is a valid combo). Choose the combined-output approach so we get rename-detection AND line counts in one pass.

- [ ] **A.1.2 — GixRepo: compute line counts via `gix_diff::blob`.** For each `tree::Change::Modification` plus `Rewrite` (with similarity), fetch parent and current blob OIDs, run a unified diff, count added/deleted hunks. For `Addition`, set `loc_added = total_lines(blob)`, `loc_deleted = 0`. For `Deletion`, the reverse. `gix_diff` provides the line-counting algorithm; do NOT roll our own. Match Git's default whitespace handling (`-w` is OFF by default). The current `gix_change_to_file_change` (`gix_repo.rs:239`) becomes `fn gix_change_to_file_change_with_loc<'a>(repo: &'a gix::Repository, change: gix::object::tree::diff::Change<'a, '_, '_>) -> Result<FileChange>` — needs the `&Repository` for blob lookups.

- [ ] **A.1.3 — Regression tests.** Add `crates/codelore-lib/tests/loc_counts_test.rs` driving both walkers against the differential fixture (which has known multi-commit history) and asserting non-zero `loc_added` + `loc_deleted` totals. The two walkers must produce IDENTICAL counts for the same commit on the same file (differential-test invariant already established for other fields).

- [ ] **A.1.4 — Code-maat parity verification.** Re-run `code_maat_parity_test.rs::*churn*` with the fix and confirm non-trivial counts. If code-maat's reference output for these fixtures was also zero (because the original log was `--name-status`), regenerate it with `--numstat`.

**Files:** `crates/codelore-lib/src/repo/gix_repo.rs` (~80 LOC), `crates/codelore-lib/src/repo/git_cli_repo.rs` (~60 LOC), `crates/codelore-lib/tests/loc_counts_test.rs` (new, ~80 LOC), `tests/fixtures/` re-record. Total: ~220 LOC + fixture refresh.

## Theme B — Architectural design (rename lineage)

### Task B.1 — Canonical rename-lineage CTE

**Validated state:**
- `changes.rename_from` is captured at ingest (verified per the roadmap entry: "data captured, queries don't follow yet"). Once A.4 lands, GixRepo also populates it.
- All 21 analyses' SQL group on raw `changes.path`. Specifically confirmed: `revisions.rs:15`, `coupling.rs:75,86`, `churn.rs:39,44`, `code_health.rs:38,43,48,58,65,67`, `hotspots.rs:48,54`, `code_age.rs:22`, `entity_ownership.rs:27`, `main_dev.rs:85,99`, `ownership.rs:33,38`, `entity_effort.rs:30`, `messages.rs:28`.
- `rename_from` is not referenced in ANY analysis SQL.

**Impact:** renamed files have their revision history split. `file-old.rs` has N revisions before rename; `file-new.rs` has M revisions after. Hotspot ranking under-counts heavily-renamed files (refactored code). Coupling pairs split across rename boundaries.

**Why design-heavy:** rename chains can have CYCLES (A → B → A) in pathological histories; the CTE resolver must detect and break them deterministically. The canonical-path resolution must be stable across runs (same input → same canonical path) for the cache to work.

#### Sub-tasks

- [ ] **B.1.1 — Define canonical-lineage CTE.** Add a single `path_lineage` view in `crates/codelore-lib/src/facts/views.rs` (or wherever views live — verify before writing). The view materializes `original_path → canonical_path` via recursive CTE: `WITH RECURSIVE lineage(orig, canon, depth) AS (SELECT path, path, 0 FROM changes WHERE rename_from IS NULL UNION ALL SELECT l.orig, c.path, l.depth + 1 FROM lineage l JOIN changes c ON l.canon = c.rename_from WHERE l.depth < 50) SELECT orig, canon FROM lineage WHERE depth = (SELECT MAX(depth) FROM lineage l2 WHERE l2.orig = lineage.orig)`. The `depth < 50` is the cycle-breaker (no realistic file has 50+ renames). The `MAX(depth)` step picks the latest rename in each chain.

- [ ] **B.1.2 — Add a `canonical_path` column to every aggregation.** Each analysis SQL gets `JOIN path_lineage ON changes.path = path_lineage.orig` and groups by `path_lineage.canon` instead of `changes.path`. The output `entity` field shows the canonical (post-rename) path. The wider impact: 13 analysis SQLs change, all parity tests need regenerated reference outputs.

- [ ] **B.1.3 — Behavior toggle.** Add `Options.use_canonical_lineage: bool` (default `true`). When `false`, fall back to the legacy raw-path grouping. This preserves the code-maat parity surface for users who want EXACT code-maat reproducibility. Document the trade-off in `advanced-usage.md`.

- [ ] **B.1.4 — Regression test.** `tests/rename_lineage_test.rs`: fixture with `foo.rs` revised twice → renamed to `bar.rs` → revised once more. Assertions:
  - With `use_canonical_lineage = true` (default): `revisions` shows ONE entity `bar.rs` with 4 revisions.
  - With `use_canonical_lineage = false`: `revisions` shows TWO entities (`foo.rs` with 3, `bar.rs` with 1), matching code-maat.
  - Cycle case: `a.rs → b.rs → a.rs` resolves deterministically (CTE depth picks the latest; document the rule).

- [ ] **B.1.5 — Cache impact: schema version bump.** Same bundle as A.1 and A.4.

**Files:** `facts/views.rs` (~40 LOC new view), all 13 analysis SQLs (each gains a JOIN + GROUP BY rewrite — ~5-10 LOC each, total ~80-130 LOC), `options.rs` (1 field), `args.rs` (1 flag, opt-out: `--no-canonical-lineage`), `rename_lineage_test.rs` (~200 LOC), parity tests' golden files refresh.

**Cache impact:** YES (significant — every analysis's output changes for any repo with renames).

**Effort:** XL (full day). The CTE design is 30 min; the parity-test golden regeneration is the long tail. **Risk:** if any current parity test relies on the rename-split behavior for its expected output, fix the test rather than weaken the lineage logic.
